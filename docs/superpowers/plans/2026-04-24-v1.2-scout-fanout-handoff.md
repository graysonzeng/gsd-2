## 一、目标

在 P1（Research）阶段实现 **scout fan-out**：当 `research-slice` 被调度时，启动 N 个并行 scout subagent 进行代码库探索，然后将输出合并为单一 research artifact。

**这是唯一需要 kernel delta 的版本。**

## 三、当前 P1 相关代码状态

### 3.1 Dispatch 规则（`auto-dispatch.ts`）

P1 涉及的 dispatch 规则链：
- `pre-planning (no research) → research-milestone`（line ~436）
- `planning (multiple slices need research) → parallel-research-slices`（line ~466）
- 以及单 slice research 规则

这些规则检查 `prefs?.phases?.skip_research`、slice RESEARCH 文件是否存在来决定是否分派 research。

### 3.2 Pre-dispatch 挂钩点

当前 `PreDispatchHookConfig.action` 支持：`"modify" | "skip" | "replace" | "advise"`

v1.2 需要新增：`"fan-out"`

### 3.3 `PreDispatchResult` 当前定义

```typescript
interface PreDispatchResult {
  action: "proceed" | "skip" | "replace" | "advise";
  prompt?: string;
  unitType?: string;
  unitId?: string;
  advisedUnitType?: string;
  advisedUnitId?: string;
  model?: string;
  firedHooks: string[];
}
```

### 3.4 Profile-map P1 定义

```typescript
{ phase: "P1", units: ["research-milestone", "research-slice"], gating: "soft" }
```

### 3.5 Composed-lite `p1-research.ts` 参考实现

位于 `feat/composed-lite-runtime-owned` 分支的 `src/resources/extensions/gsd/composed-lite/phases/p1-research.ts`（218 行）。核心行为：

- **SCOUT_TASKS**：3 个固定 scout（`codebase_scan`、`constraints_risks`、`prior_art`）
- **并行执行**：`Promise.allSettled()` 启动 3 个 scout subagent
- **Scout 约束**：通过 `--append-system-prompt` 注入 guard prompt，限制 `--tools read,grep,find,ls,bash`
- **结果合并**：将各 scout 输出拼接为 `research-brief` artifact（markdown 格式）
- **审计**：每个 scout 的 `subagent_call` / `subagent_result` 写入 audit log
- **Raw log**：每个 scout 的 raw output 写到 `.gsd/composed-lite/logs/raw/` 目录
- **错误处理**：任一 scout 的 `terminalError` 导致该 scout 标记为失败

## 四、设计空间（需要在规划中决策）

### 4.1 Kernel delta：`PreDispatchHookConfig.action: "fan-out"` vs 替代方案

**Spec 原始设计**：在 `PreDispatchHookConfig` 上新增 `action: "fan-out"`，但这会改变整个 pre-dispatch 执行引擎。

**替代方案需要评估**：

| 方案 | Kernel 改动 | 优缺点 |
|---|---|---|
| A. `action: "fan-out"` 新 pre-dispatch action | `types.ts` + `rule-registry.ts` + `auto-dispatch.ts` + `auto/phases.ts` | Spec 原始设计；通用性强但 kernel 风险高 |
| B. 新 post-unit hook（`after: ["research-slice"]`）+ builtin 短路 | 仅 `phase-discipline/` 内 | 零 kernel delta；但 fan-out 发生在 unit 完成后而非调度前 |
| C. 扩展 `PreDispatchResult` 新增 `fanOutSpecs` 返回值 | `types.ts` + `rule-registry.ts` 消费侧 | 中等 kernel delta；pre-dispatch hook 返回 fan-out 计划，由 engine 执行 |
| D. `action: "replace"` 替换为自定义 builtin 执行 | 无新 action type | 利用已有 replace 语义 + builtin 短路 |

**关键取舍**：
- 方案 A 最通用但改动最大，对 `auto-dispatch.ts` / `auto/phases.ts` / `rule-registry.ts` 都有侵入
- 方案 B 最安全（零 kernel），但语义上 fan-out 应该发生在 dispatch 阶段而非 post-unit
- 方案 C/D 是折中路径

### 4.2 Scout 配置

- **Scout 数量**：固定 3（同 composed-lite）还是可配置？
- **Scout 模型**：使用 hook config 的 `model` 还是新增字段？
- **Scout 任务定义**：硬编码 3 个 focus 还是可扩展？

### 4.3 结果合并

- 合并格式：markdown brief vs YAML structured output
- 合并逻辑：简单拼接 vs 去重/摘要

### 4.4 Artifact 路径

- 输出路径：`.gsd/milestones/{mid}/slices/{sid}/RESEARCH-BRIEF.md` 还是 `.gsd/milestones/{mid}/RESEARCH`（当前 `auto-dispatch.ts` 检查的是 `resolveMilestoneFile(basePath, mid, "RESEARCH")`）
- Raw log 路径：`.phase-discipline/` vs `.gsd/` 下其他位置

### 4.5 与 OQ-7/OQ-10 的交互

已有的 `writeObservabilityLog` 和 `writeReviewerRawLog` 可以复用模式（不一定直接调用）来记录 scout 的结构化 metrics 和 raw output。

## 六、约束与纪律

1. **独立 track**：v1.2 的 kernel delta 不应与 v1.1/v1.3/v1.4 混在同一 commit
2. **最小 kernel 侵入**：方案选择应优先最小化 `auto-dispatch.ts` / `rule-registry.ts` / `auto/phases.ts` 的改动量
3. **不破坏现有 advise 语义**：`honour-phase-discipline-advice` prefix rule 必须继续工作
4. **共享 harness 复用**：尽量复用 `shared-harness/subagent-spawn.ts` 而非重新实现
5. **观测面对齐**：scout 的 metrics 和 raw log 应与 OQ-7/OQ-10 已有模式对齐
6. **Spec 原话**："v1.2 requires new `PreDispatchHookConfig.action: "fan-out"` kernel delta" — 但**方案 B/C/D 也应被评估**，如果能以更小侵入达成同等效果
