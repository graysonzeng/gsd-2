## 三、v1.1 Admission — 独立会话指南

### 目标

在 P0 阶段（`discuss-milestone` 完成后）运行 admission-checklist post-unit hook，验证 milestone 是否具备开始条件。

### Spec 来源

- `docs/superpowers/specs/phase-discipline-preset.md` §12 v1.1 行
- `docs/superpowers/roadmap/phase-discipline-roadmap.md` §3

### 实现形态（spec §12）

> New post-unit hook `phase-discipline-admission` with 6–8 checklist items; `retry_on` pattern if checklist has unchecked items

### 具体步骤

1. **`preset.ts`** — 在 `phaseDiscipline8StepPostUnitHooks` 数组中新增 hook：
   ```typescript
  {
    name: "phase-discipline-admission",
    after: ["discuss-milestone"],
    prompt: "...", // 6-8 项 checklist，检查 milestone 是否具备开始条件
    artifact: "ADMISSION-CHECKLIST.md",
    retry_on: "ADMISSION-RETRY.md",
    max_cycles: 2,
  }
  ```
   - **注意**：admission 保持 **prompt-only**，不要给它挂 `builtin` 标记；`builtin` 仅保留给存在 runtime handler 的 hook
2. **`PHASE_DISCIPLINE_PRESET_HOOK_NAMES`** — 添加 `admission: "phase-discipline-admission"`
3. **Prompt 设计**（核心）：prompt 应要求 agent 检查：
   - milestone 目标是否明确（有具体 deliverable）
   - 依赖项是否就绪（无 blocking 前置 milestone）
   - scope 是否合理（不超过 5 个 slice）
   - 验收标准是否可测（有 verification 命令或手动验收步骤）
   - 风险是否已识别
   - milestone 估算是否合理
   - 关键未知项是否已显式识别
   然后输出 markdown checklist（`- [x]` / `- [ ]`）。
   - prompt 必须写明精确产物路径：
     - `.gsd/milestones/{milestoneId}/ADMISSION-CHECKLIST.md`
     - `.gsd/milestones/{milestoneId}/ADMISSION-RETRY.md`
   - checklist 末尾保留 `Admission Decision: pass|needs-rework`
   - 并明确要求：**当且仅当** Decision 为 `needs-rework` 时写 `ADMISSION-RETRY.md`
   - 建议显式提示 agent 优先阅读当前 milestone discussion / roadmap / 现有 planning artifacts，降低空评风险
4. **`rule-registry.ts`** — 修复 prompt-driven retry 的第二轮重跑语义：
   - 在 `_handleHookCompletion()` 检测到 `retry_on` 且 `currentCycle < maxCycles` 时，先删除当前 hook 的主 `artifact`（如果存在），再设置 `retryPending`
   - 这样下一轮 `checkPostUnitHooks()` 不会被 idempotency 的“artifact 已存在”提前跳过
   - 这是一个对 prompt-driven hook 通用生效的确定性修复，不为 admission 单独引入 runtime handler
5. **测试**：在 `phase-discipline/tests/` 新增 `admission.test.ts`
   - 测试 hook 通过 preset merge 正确注入
   - 测试 prompt 执行后能生成 checklist artifact
   - 测试 unchecked 项触发 retry
   - 测试 retry 后 cycle 2 能再次 dispatch admission
   - 测试 `max_cycles: 2` 耗尽后不再继续重派
   - admission 相关断言不要依赖全局 `Browser tool safety` 注入文案
6. **改动边界**：本轮允许改 `preset.ts`、`rule-registry.ts`、相关 admission 测试，以及受 admission `builtin` 语义影响的集成/偏好断言；仍不引入 admission 专属 runtime handler

### 本轮修订说明（吸收 2026-04-24 review）

- **采纳 P0-1**：prompt 必须给出精确 artifact 路径，否则 registry 无法稳定识别 artifact / retry
- **采纳 P0-2**：admission 去掉 `builtin`，与“prompt-only、无 runtime handler”的事实对齐
- **采纳 P1-3**：不采用仅靠 prompt 删除文件的软修复，改为 registry 层清理 stale artifact 的确定性方案
- **部分采纳 P1-4**：保留 `Admission Decision` 行，但只作为 agent-facing 自检语义；系统仍以 retry artifact 为准
- **采纳 P1-6 中的关键测试项**：补 cycle-2 与 max-cycles 覆盖

### 风险（roadmap §3.3）

- checklist 空洞化 / 直接照搬 composed-lite 文案 → prompt 需仔细设计，与 composed-lite `phases/p0-admission.ts` 对比但不照搬
- prompt-driven retry 仍以 `retry_on` artifact 作为唯一机器信号，`Admission Decision` 仅为辅助可读性，不做 runtime 解析

### 退出标准

- ✅ 新增测试通过
- ✅ typecheck 通过

## 四、v1.3 Impl-plan Validator — 独立会话指南

### 目标

在 P2→P3 边界验证 `plan-slice` 输出的实现计划 frontmatter 符合增强 schema（含 `rollback_hint`、`acceptance`、`files[]`），并将 P2/P3 gating 从“artifact 存在即可放行”收紧为“**只有 validator artifact 明确 `Result: pass` 才放行**”。同时把 `files[]` 的“非空数组”要求在 tool / MCP / validator 三层对齐。

### Spec 来源

- `docs/superpowers/specs/phase-discipline-preset.md` §12 v1.3 行
- §3.1b 表格 P2/P3 列的 "v1.3: impl-plan-YAML validator"

### 实现形态（spec §12）

> Tighten `gsd_plan_slice` schema to require `rollback_hint`, `acceptance`, `files[]` per task; post-unit hook validates

### 具体步骤

1. **新文件 `phase-discipline/impl-plan-validator.ts`** — 导出验证函数：
   ```typescript
   export interface ImplPlanValidationResult {
     valid: boolean;
     errors: string[];
   }
   export function validateImplPlan(planContent: string): ImplPlanValidationResult
   ```
   验证 plan-slice 输出中每个 task 包含：
   - `rollback_hint: string`（回滚提示）
   - `acceptance: string`（验收标准）
   - `files: string[]`（预期修改文件列表）
2. **`preset.ts`** — 新增 post-unit hook：
   ```typescript
   {
     name: "phase-discipline-impl-plan-validator",
     after: ["plan-slice"],
     prompt: "Validate the implementation plan...",
     artifact: "IMPL-PLAN-VALIDATION.md",
     retry_on: "IMPL-PLAN-RETRY.md",
     max_cycles: 2,
   }
   ```
3. **`PHASE_DISCIPLINE_PRESET_HOOK_NAMES`** — 添加 `implPlanValidator: "phase-discipline-impl-plan-validator"`
4. **`profile-map.ts`** — 保持 P2 和 P3 为 `strict`，`completionArtifact` 继续指向 `IMPL-PLAN-VALIDATION.md`：
   ```typescript
   // P2 / P3: gating 都依赖 impl-plan validator artifact
   { phase: "P2", units: ["plan-slice", "refine-slice"], gating: "strict",
     completionArtifact: ".gsd/milestones/{mid}/slices/{sid}/IMPL-PLAN-VALIDATION.md" },
   { phase: "P3", units: ["plan-slice"], gating: "strict",
     completionArtifact: ".gsd/milestones/{mid}/slices/{sid}/IMPL-PLAN-VALIDATION.md" },
   ```
5. **`profile-dispatch.ts`** — 收紧 strict gating 语义：
   - 不能只用 `existsSync(IMPL-PLAN-VALIDATION.md)` 判断完成
   - 必须读取 artifact 内容，只有存在 `- Result: pass` 时才视为 P2/P3 已完成
   - `Result: fail`、缺失 `Result`、文件不存在三种情况都应继续 `advise plan-slice`
6. **schema / tool 一致性**：
   - `tools/plan-slice.ts`：`tasks[i].files` 必须是**非空**字符串数组
   - `bootstrap/db-tools.ts`：`files` 参数 schema 加 `minItems: 1`
   - `packages/mcp-server/src/workflow-tools.ts`：`files` 参数 schema 改为非空数组（至少 1 项）
   - 保持 validator 侧 `files.length === 0` 检查作为防御性兜底
7. **测试**：
   - `phase-discipline/tests/impl-plan-validator.test.ts` — 验证 schema 检查逻辑
   - `phase-discipline/tests/profile-dispatch.test.ts` — 增加 negative case：artifact 存在但 `Result: fail` 时仍应 `advise plan-slice`
   - `src/resources/extensions/gsd/tests/plan-slice.test.ts` / `workflow-mcp.test.ts` / `workflow-tool-executors.test.ts`（按需最小补充）——锁定 `files[]` 非空约束
8. **`preferences-validation.ts`** — 无需改动（继续复用既有 post-unit hook + builtin 保留路径）

### 风险（roadmap §3.3）

- schema 一次收得过死 → 仅 require `rollback_hint`/`acceptance`/`files[]`，不验证内容质量
- 字段只要"存在"不要"质量" → v1.3 scope 仅做 structural validation

## 五、v1.4 Verify-fuse — 独立会话指南

### 目标

当 `validate-milestone` 失败时，阻止 milestone close（而非当前的 carry-forward 行为），实现 P5 strict 验证。

### Spec 来源

- `docs/superpowers/specs/phase-discipline-preset.md` §12 v1.4 行
- §3.1b 表格 P5 列

### 实现形态（spec §12）

> Preference `verify_fuse_on_fail?: boolean`; when true, `validate-milestone` failure blocks milestone close instead of carry-forward

### 具体步骤

1. **`preferences-types.ts`** — `GSDPreferences` 新增字段：
   ```typescript
   verify_fuse_on_fail?: boolean;
   ```
   同时在 `KNOWN_PREFERENCE_KEYS` 数组中添加 `"verify_fuse_on_fail"`
2. **`preferences-validation.ts`** — 添加验证：
   ```typescript
   if (preferences.verify_fuse_on_fail !== undefined) {
     if (typeof preferences.verify_fuse_on_fail === "boolean") {
       validated.verify_fuse_on_fail = preferences.verify_fuse_on_fail;
     } else {
       errors.push("verify_fuse_on_fail must be a boolean");
     }
   }
   ```
3. **新文件 `phase-discipline/verify-fuse.ts`** — 导出共享判断与 built-in hook 执行函数：
   ```typescript
   export function shouldBlockMilestoneClose(input: {
     basePath: string;
     milestoneId: string;
     validationPassed: boolean;
   }): { blocked: boolean; reason?: string }
   ```
   - 读取 preferences，当 `verify_fuse_on_fail === true` 且 `validationPassed === false` 时返回 `blocked: true`
   - 同文件额外导出：
     - `readMilestoneValidationVerdict(basePath, milestoneId)`：读取 `VALIDATION` verdict
     - `runPhaseDisciplineVerifyFuseHook(...)`：写 `VERIFY-FUSE.md` 审计产物
   - **语义约束**：verify-fuse 仅对显式失败 verdict 生效，即 `needs-attention` / `needs-remediation`；`null` / `unknown` / 缺失 verdict 一律视为“无明确失败信号”，不阻断 milestone close
4. **`preset.ts`** — 新增 built-in post-unit hook（在 `validate-milestone` 后触发），仅负责写审计 artifact，不负责 retry：
   ```typescript
   {
     name: "phase-discipline-verify-fuse",
     after: ["validate-milestone"],
     prompt: "Record the verify-fuse decision for the latest validate-milestone result.",
     artifact: "VERIFY-FUSE.md",
     builtin: "phase-discipline-verify-fuse",
   }
   ```
5. **`PHASE_DISCIPLINE_PRESET_HOOK_NAMES`** — 添加 `verifyFuse: "phase-discipline-verify-fuse"`
6. **`profile-map.ts`** — 保持 P5 `gating: "soft"` 不变；真实阻断点放在 dispatch guard：
   - `completing-milestone → complete-milestone` 规则中读取 `VALIDATION` verdict
   - 当 verdict 为显式失败且 `verify_fuse_on_fail === true` 时，调用 `shouldBlockMilestoneClose(...)` 返回 `{ action: "stop" }`
   - 既有 `needs-remediation` fallback guard 保留；但当 verify-fuse 开启时，由 verify-fuse guard 优先拦截并给出对应 reason
   - **结论**：v1.4 的真实实现是 **dispatch guard（硬阻断） + preset hook（审计产物）**，而不是依赖 hook retry 驱动流程控制
7. **测试**：
   - `phase-discipline/tests/verify-fuse.test.ts` — 验证 fuse 逻辑
   - preference 开启/关闭两种路径
   - validation pass / fail 组合
   - `unknown` / 缺失 verdict 时 hook 写出 `Validation Verdict: unknown` 且 `Close Blocked: no`
   - `remediation-completion-guard.test.ts` 补 `verify_fuse_on_fail + needs-remediation` 优先级 case，证明新 guard 先于旧 fallback guard 生效
   - 不再为 `VERIFY-FUSE-RETRY.md` 编写“会被 engine 消费”的测试；verify-fuse 不参与 retry 链路

### 本轮修订说明（吸收 2026-04-24 review）

- **采纳 P0-1**：删除 verify-fuse 的伪 retry 设计；`retry_on + max_cycles: 1` 在现有 engine 语义下不可达，继续保留只会制造误导
- **采纳 P1-1**：dispatch guard 不再对 `verdict === "pass"` 走冗余的 `shouldBlockMilestoneClose(...)` 调用
- **采纳 P1-3**：方案显式声明 verify-fuse 只响应显式失败 verdict；`unknown` / 缺失 verdict 不阻断
- **采纳 P1-4**：补 `needs-remediation` 优先级与 `unknown` verdict 边界测试
- **采纳 P2-7**：方案文本同步为真实实现模型：`auto-dispatch.ts` 的 close guard 负责硬阻断，preset hook 负责审计输出
- **本轮不做 P1-5 / P2-6**：artifact 过期问题与 guard 抽取属于后续迭代，不混入本轮收敛补丁

### 风险（roadmap §3.3）

- 默认开太早 → `verify_fuse_on_fail` 默认为 `false`（需 opt-in）
