采用 **P0（合并前必须修）/ P1（强烈建议在此 PR 或紧随补丁修）/ P2（优化，不阻塞）/ P3（观察项）** 四级。

### P0-1 ❌ admission prompt 未显式告知 artifact 写入路径

**证据**：

```4:12:src/resources/extensions/gsd/phase-discipline/preset.ts
function buildPhaseDisciplineAdmissionPrompt(): string {
  return [
    "Run the phase-discipline admission checklist for milestone {milestoneId} after discuss-milestone completes.",
    "Review the milestone goal, current context, and any existing planning artifacts before deciding whether execution should start.",
    "Write ADMISSION-CHECKLIST.md as markdown using 6-8 checklist items with `- [x]` / `- [ ]` format and a brief rationale under each item.",
    "The checklist must explicitly cover: concrete deliverable clarity, dependency readiness/no blocking prerequisite milestone, scope size staying within 5 slices, measurable acceptance criteria with verification commands or manual validation steps, identified risks, reasonable milestone estimate, and any critical unknowns that still need clarification.",
    "End the checklist with `Admission Decision: pass` or `Admission Decision: needs-rework`.",
    "If any checklist item is unchecked, also write ADMISSION-RETRY.md summarizing the missing start conditions and the exact follow-up needed before retry. If all items pass, do not create the retry artifact.",
  ].join("\n\n");
}
```

`rule-registry` 通过 `resolveHookArtifactPath(basePath, triggerUnitId, "ADMISSION-CHECKLIST.md")` 期望 artifact 落到 `.gsd/milestones/{mid}/ADMISSION-CHECKLIST.md`（同理 `ADMISSION-RETRY.md`）。但 prompt 只说 "Write ADMISSION-CHECKLIST.md"，没有路径信息。

**影响**：

- agent 若写到工作区根目录或 `.gsd/` 根目录 → `existsSync(artifactPath)` 永远 false → idempotency 失效 → 每次 `discuss-milestone` 完成都重复分派 admission 直到 `max_cycles` 耗尽
- retry 同理：`ADMISSION-RETRY.md` 写在错误位置会被 registry 忽略，retry 不触发

**修复建议**（二选一）：

- **方案 A（推荐）**：prompt 末尾追加一行
  ```
  Write the checklist to `.gsd/milestones/{milestoneId}/ADMISSION-CHECKLIST.md`. If retry is needed, also write `.gsd/milestones/{milestoneId}/ADMISSION-RETRY.md`. Use these exact paths so the hook registry can find them.
  ```
- **方案 B**：在 prompt 生成时调用 `resolveHookArtifactPath` 预先计算绝对路径并模板替换 `{artifactPath}` / `{retryPath}`，消除 agent 的路径推断需求

对照 v1 已有 hook：`code-review` / `design-review` 走 built-in 代码路径，artifact 由 runtime 直接写入，无此问题；`findings-to-memories` 虽也是 prompt-only 但 prompt 已明确"write the memory file under `.gsd/memories/...`"。admission 是目前唯一未告知写入路径的 prompt-only hook。

### P0-2 ❌ admission 的 `builtin` 字段悬空，与其他 preset hook 语义不一致

**证据**：

```30:30:src/resources/extensions/gsd/phase-discipline/preset.ts
    builtin: PHASE_DISCIPLINE_PRESET_HOOK_NAMES.admission,
```

但 `maybeRunPhaseDisciplineBuiltInHook`（`reviewer-hook.ts` 内）只 switch 以下几个 builtin 值：

- `phase-discipline-code-review`
- `phase-discipline-design-review`

`maybeRunPhaseDisciplineImplPlanBuiltInHook`（`impl-plan-validator.ts`）处理 `phase-discipline-impl-plan-validator`；`maybeRunPhaseDisciplineVerifyFuseBuiltInHook`（`verify-fuse.ts`）处理 `phase-discipline-verify-fuse`。

**没有任何地方处理 `phase-discipline-admission`**，因此 `run-unit.ts` 中所有 `maybeRun*` 调用都返回 false，admission 最终走通用 prompt 路径（`pi.sendMessage(prompt, ...)`）——这本身符合 plan §3 "prompt-only" 的目标，**但 `builtin` 字段的存在让整段设计误导**：

| Hook | 有 `builtin` 字段 | 有 runtime handler | 实际路径 |
|------|-------------------|--------------------|---------|
| admission | ✅ | ❌ | prompt-only |
| code-review | ✅ | ✅ (reviewer-hook.ts) | built-in 短路 |
| design-review | ✅ | ✅ (reviewer-hook.ts) | built-in 短路 |
| impl-plan-validator | ✅ | ✅ (impl-plan-validator.ts) | built-in 短路 |
| verify-fuse | ✅ | ✅ (verify-fuse.ts) | built-in 短路 |
| findings-to-memories | ❌ | ❌ | prompt-only |

admission 是**唯一一个"`builtin` 字段有值但没有对应 handler"** 的 hook。对照 `phase-discipline/README.md`：

```22:30:src/resources/extensions/gsd/phase-discipline/README.md
## Built-in hooks

Only three preset-owned hooks have code-backed behavior:

- `phase-discipline-profile-dispatch`
- `phase-discipline-code-review`
- `phase-discipline-design-review`

They are identified at runtime through the internal `builtin` marker added by the preset merge path. This avoids treating user-authored shadow hooks with the same `name` as built-in hooks.
```

README 明确说"`builtin` 是识别 runtime 特殊处理的标记"。admission 挂 `builtin` 字段但无代码路径，直接违反这段约定。

**影响**：

- 将来新人读代码看到 admission 的 `builtin: "phase-discipline-admission"` 会以为有 runtime handler，浪费 grep / 调试时间
- 若后续（如 v1.x）要为 admission 加 runtime handler（例如辅助删除旧 artifact、解析 Decision 行），会在不知情的情况下修改行为语义
- 让 "shadow hook 不会被误判为 built-in" 的防御失效（见 README 第 30 行）：若用户写一个同名 `phase-discipline-admission` 的 shadow hook，也会因为带有 `builtin` 字段被 preferences 端 preserve，继而在某次 refactor 里被短路

**修复建议**（推荐 A）：

- **方案 A（推荐）**：从 admission 配置里**移除 `builtin` 字段**，和 `findings-to-memories` 保持一致。同时更新：
  - `preferences.test.ts` 中对 `phase-discipline-admission` 的 built-in 断言移除（或改为断言"admission 不带 `builtin` 标记"）
  - `phase-discipline-integration.test.ts` 对应断言更新
- **方案 B**：保留 `builtin` 字段但在 README "Built-in hooks" 段落明确"admission 的 `builtin` 是 preset-ownership 标记而非 runtime handler 标记"；并在 `admission.test.ts` 增加一条 negative test：
  ```ts
  // Guard: admission must remain prompt-driven.
  // If a runtime handler is ever added for phase-discipline-admission, this test fails
  // and the README's "Built-in hooks" section must be updated.
  ```

方案 A 更干净。方案 B 只在有明确路径规划要在 v1.x 给 admission 加 runtime handler 时才合理。

### P1-3 ⚠️ retry 路径在 cycle 2 实际不会再次执行 admission（pre-existing 设计 gap，admission 放大）

**证据**：

```193:203:src/resources/extensions/gsd/rule-registry.ts
// Check idempotency — if artifact already exists, skip
if (config.artifact) {
  const artifactPath = resolveHookArtifactPath(basePath, triggerUnitId, config.artifact);
  if (existsSync(artifactPath)) continue;
}

// Check cycle limit
const cycleKey = `${config.name}/${triggerUnitType}/${triggerUnitId}`;
const currentCycle = (this.cycleCounts.get(cycleKey) ?? 0) + 1;
const maxCycles = config.max_cycles ?? 1;
if (currentCycle > maxCycles) continue;
```

```239:269:src/resources/extensions/gsd/rule-registry.ts
private _handleHookCompletion(basePath: string): HookDispatchResult | null {
  const hook = this.activeHook!;
  const hooks = resolvePostUnitHooks(basePath);
  const config = hooks.find(h => h.name === hook.hookName);

  // Check if retry was requested via retry_on artifact
  if (config?.retry_on) {
    const retryArtifactPath = resolveHookArtifactPath(basePath, hook.triggerUnitId, config.retry_on);
    if (existsSync(retryArtifactPath)) {
      const cycleKey = `${config.name}/${hook.triggerUnitType}/${hook.triggerUnitId}`;
      const currentCycle = this.cycleCounts.get(cycleKey) ?? 1;
      const maxCycles = config.max_cycles ?? 1;

      if (currentCycle < maxCycles) {
        this.activeHook = null;
        this.hookQueue = [];
        this.retryPending = true;
        this.retryTrigger = {
          unitType: hook.triggerUnitType,
          unitId: hook.triggerUnitId,
          retryArtifact: config.retry_on,
        };
        return null;
      }
    }
  }
```

**流程模拟**（admission 第一次写入 checklist 但 Decision 为 needs-rework）：

1. `discuss-milestone M001` 完成 → `checkPostUnitHooks` 入队 admission → `_dequeueNextHook` 发现 `ADMISSION-CHECKLIST.md` 不存在 → dispatch admission（cycle=1）
2. admission hook unit 执行：agent 写入 `ADMISSION-CHECKLIST.md` 和 `ADMISSION-RETRY.md`
3. `hook/phase-discipline-admission` 完成 → `_handleHookCompletion` 发现 retry 文件 → `retryPending=true`，`retryTrigger = { unitType: "discuss-milestone", unitId: "M001", retryArtifact: "ADMISSION-RETRY.md" }`
4. scheduler 读取 `consumeRetryTrigger()` → 重新分派 `discuss-milestone M001`
5. `discuss-milestone` 重跑完成 → `checkPostUnitHooks("discuss-milestone", "M001", ...)` → `_dequeueNextHook` 再次检查 `ADMISSION-CHECKLIST.md` → **文件仍存在（cycle 1 写的，无人删除）** → `continue` → admission **不会再分派** → `max_cycles: 2` 配置形同虚设

**为何 reviewer-hook（code/design）不受此问题困扰**：reviewer-hook 走 `maybeRunPhaseDisciplineBuiltInHook` 短路路径，`run-unit.ts` 分派 hook unit 时直接在 runtime 里执行完成，不经过 `rule-registry.evaluatePostUnit` → `_dequeueNextHook` 的 idempotency 检查的第二次调用（idempotency 检查只在第一次入队时生效，built-in handler 在 dispatch 的那一瞬间已经把 artifact 写入了，也不会再来第二次），同时 reviewer-hook 每次都会覆盖 artifact 内容。**admission 是 prompt-only，没有 runtime handler 管理 artifact 生命周期**，因此 idempotency 检查成为真正的阻碍。

**测试盲区确认**：`admission.test.ts` 第三个 case 只验证"retry 被请求"（`isRetryPending() === true` 和 `consumeRetryTrigger()` 返回正确内容），但**没有**模拟 scheduler 重新分派 `discuss-milestone` 再次调用 `checkPostUnitHooks` 并断言 admission 二次分派。这个场景完全未覆盖，因此测试全绿但实际 retry 路径在 cycle 2 不会跑。

**影响**：

- `max_cycles: 2` 的行为与用户预期不一致；plan §3 隐含"最多两轮收敛"但实际只能一轮
- 若 admission 第一次评估 = needs-rework，用户补完资料、重跑 `discuss-milestone` 后，希望 admission 重新评估——但 admission 永远不会再跑，除非用户手动删除 `ADMISSION-CHECKLIST.md`

**修复建议**（三选一，按侵入性排序）：

- **方案 A（prompt 层，最小改动）**：在 admission prompt 中追加一条指令：
  > If you need to write `ADMISSION-RETRY.md` (any item unchecked), also ensure `ADMISSION-CHECKLIST.md` is deleted or overwritten with the still-failing checklist *before* finishing this hook, so the next admission cycle can evaluate freshly.

  **缺点**：依赖 agent 正确理解并执行删除指令；不是确定性保障。
- **方案 B（registry 层，推荐）**：在 `rule-registry._handleHookCompletion` 的 retry 触发分支里，**在 `retryPending = true` 之前删除 `artifactPath`**：
  ```ts
  if (currentCycle < maxCycles) {
    // Clear stale artifact so the next cycle re-evaluates instead of being skipped by idempotency.
    if (config.artifact) {
      const artifactPath = resolveHookArtifactPath(basePath, hook.triggerUnitId, config.artifact);
      if (existsSync(artifactPath)) rmSync(artifactPath, { force: true });
    }
    this.activeHook = null;
    this.hookQueue = [];
    this.retryPending = true;
    this.retryTrigger = { ... };
    return null;
  }
  ```

  **优点**：一处修改对所有 prompt-driven retry hook（admission、将来可能的 v1.3 prompt 型 validator 替代方案）统一生效；built-in hook 自管 artifact 不受影响（它们在 retry 后仍会被短路覆盖，无论文件是否存在）。

  **风险**：影响面跨越 v1 基线行为。需要在 PR 说明里明确列出，且为 reviewer-hook 的 retry 加回归测试确认行为一致。
- **方案 C（为 admission 引入 built-in handler）**：新建 `src/resources/extensions/gsd/phase-discipline/admission.ts`，负责 artifact 骨架 + cycle-aware cleanup；prompt 继续由 agent 填内容。

  **缺点**：违背 plan §3"prompt-only"原则，超出 v1.1 范围。

**推荐落地顺序**：若 PR 要尽快合并，先选 A 保证"大多数情况工作"并在 admission.test.ts 加一个 "cycle 2 re-dispatch" 测试（即使因方案 A 依赖 agent 而该测试得用手动删除 stub 来模拟）；v1.2 或紧随补丁落地方案 B。

### P1-4 ⚠️ admission 的 `Admission Decision` 行未被代码消费

**证据**：prompt 要求：
> End the checklist with `Admission Decision: pass` or `Admission Decision: needs-rework`.

但 `rule-registry.ts`、`profile-dispatch.ts`、`post-unit-hooks.ts` 均无任何 `Admission Decision` / `admission.decision` 解析逻辑。实际 gating 信号完全来自 `ADMISSION-RETRY.md` 是否存在。

**影响**：

- "agent 写了 `Admission Decision: needs-rework` 但忘写 `ADMISSION-RETRY.md`" → 被系统误判为"通过"继续进入 P1
- "agent 写了 `Admission Decision: pass` 但也写了 `ADMISSION-RETRY.md`"（冗余情况） → 被 retry

语义一致性依赖 agent 的自律，而非机制保障。

**修复建议**（二选一）：

- **方案 A**：保留 Decision 行作为 agent 自我检查提示；在 prompt 中强化 invariant：
  > You MUST write `ADMISSION-RETRY.md` if and only if your `Admission Decision` is `needs-rework`. These two must always agree.

  并在 admission.test.ts 增加一个"记录已知风险"的注释测试或 fixture：Decision 与 retry 文件不一致时的行为 = 以 retry 文件为准。
- **方案 B**：从 prompt 移除 `Admission Decision` 行要求，单一以 retry 文件为信号；agent 不需要写可能被系统忽略的冗余语义。

方案 A 保留可读性；方案 B 简化语义。建议 A（改 prompt 一行即可，保留 Decision 作为 agent-facing 自我检查信号）。

### P1-5 ⚠️ P0→P1 gating 未明确留白

**证据**：

```9:9:src/resources/extensions/gsd/phase-discipline/profile-map.ts
  { phase: "P0", units: ["discuss-milestone"], gating: "soft" },
```

profile-map 明确 P0 = soft，无 `completionArtifact`。spec §3.1b 同样约定"P0/P1 soft"。

**但计划 §3 隐含期望**："admission needs-rework → block P1 execution until rework"。目前 block 效果完全来自 retry 触发 `discuss-milestone` 重跑（间接通路），而非 profile-dispatch 分派时的 gating 检查。

**影响**：

- 正常时序（retry 触发正常工作）下，P0→P1 过渡被 retry 机制间接 gate，soft/strict 的差异在此场景看不出来
- 若 retry 路径有 bug（如 P1-3），admission needs-rework → retry 标记未被 consume → 下一 pre-dispatch 检查时 profile-dispatch 仍然 advise `research-milestone` → P1 立即开始，admission 的"守门"效果完全失效

**修复建议**：

- **短期（v1.1）**：在 `profile-map.ts` P0 行追加注释：
  ```ts
  // P0 admission gating is soft: the admission checklist is advisory; its
  // failure only blocks progression indirectly through the `retry_on`
  // artifact re-dispatch mechanism, not through profile-dispatch gating at
  // `research-milestone` entry.
  { phase: "P0", units: ["discuss-milestone"], gating: "soft" },
  ```

### P3-10 🔍 `builtin` 字段语义整体不一致（长期问题，非 v1.1 引入）

| 维度 | 表现 |
|------|------|
| 字段值 | 都 `=== name`，无独立语义空间 |
| 有 runtime handler 的 hook | code-review / design-review / impl-plan-validator / verify-fuse |
| 无 runtime handler 但带 `builtin` | **admission**（v1.1 新增） |
| 无 `builtin` 字段 | findings-to-memories |

从字段命名看 `builtin` = "runtime 会特殊处理"；但 admission 和 findings-to-memories 都是 prompt-only，一个带 `builtin` 一个不带，令人困惑。

**长期建议**：

- **方案 A**：统一"`builtin` = 存在 runtime handler"；admission 去除 `builtin`，findings-to-memories 保持不带
- **方案 B**：将 `builtin` 改名为 `presetOwnership: "phase-discipline"` 或 `source: "preset"`，和 runtime handler 路由彻底解耦；runtime handler 分派改用显式表格（例如 `PHASE_DISCIPLINE_RUNTIME_HOOK_HANDLERS: Record<string, Handler>`）

这不是 v1.1 阻塞项，但建议 v1.2 / v1.3 开始前统一，否则 hook 数量再增长时会累积更多不一致。
