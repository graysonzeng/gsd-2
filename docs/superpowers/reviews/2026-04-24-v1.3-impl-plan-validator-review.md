### P1-1 ⚠️ profile-dispatch 的 gating 是"文件存在"而非"Result: pass"

**证据**：

```49:59:src/resources/extensions/gsd/phase-discipline/profile-dispatch.ts
function hasPhaseCompletionArtifact(basePath: string, milestoneId: string, sliceId: string, phase: "P2" | "P3"): boolean {
  const entry = PHASE_DISCIPLINE_8STEP_SEQUENCE.find((item) => item.phase === phase);
  if (!entry?.completionArtifact) return false;
  const slicePath = resolveSlicePath(basePath, milestoneId, sliceId);
  if (!slicePath) return false;
  const fileName = entry.completionArtifact
    .replace(/^.*\/slices\/\{sid\}\//, "")
    .replace(/\{mid\}/g, milestoneId)
    .replace(/\{sid\}/g, sliceId);
  return existsSync(join(slicePath, fileName));
}
```

`hasPhaseCompletionArtifact` 仅使用 `existsSync`。而 `runPhaseDisciplineImplPlanValidatorHook` 即使校验失败，也会写 `IMPL-PLAN-VALIDATION.md`（带 `Result: fail`）：

```99:132:src/resources/extensions/gsd/phase-discipline/impl-plan-validator.ts
  const valid = errors.length === 0;
  const lines: string[] = [];
  lines.push(`# ${input.hookName}`);
  lines.push("");
  lines.push(`- Trigger: ${input.triggerUnitType} ${input.triggerUnitId}`);
  lines.push(`- Result: ${valid ? "pass" : "fail"}`);
  // ...
  ensureParentDir(artifactPath);
  writeFileSync(artifactPath, `${lines.join("\n").trimEnd()}\n`, "utf8");

  if (!valid && retryPath) {
    ensureParentDir(retryPath);
    writeFileSync(retryPath, `retry requested by ${input.hookName}\n`, "utf8");
  } else {
    clearRetryArtifact(retryPath);
  }
```

**影响**：

- cycle 1：plan-slice 产出不合规 frontmatter → validator 写 `IMPL-PLAN-VALIDATION.md`（`Result: fail`）+ 写 `IMPL-PLAN-RETRY.md` → rule-registry 触发 retry
- cycle 2：plan-slice 重跑，但 **`IMPL-PLAN-VALIDATION.md` 仍然存在**，rule-registry 的 idempotency gate（`rule-registry.ts:192-197` existsSync 检查）会跳过 validator hook 重跑 → artifact 保持 `Result: fail` → 但 `IMPL-PLAN-RETRY.md` 可能被下一轮清理逻辑抹掉吗？不会，因为 validator hook 本身被跳过
- 最后 `execute-task` 被 profile-dispatch 放行 → 但实现计划仍然不合规

**为什么实际风险有限**：

- `plan-slice.ts:140-184` 在 tool 级强制了 `rollbackHint` / `acceptance` 非空、`files` 非空字符串数组（但允许空数组，见 P2-1）
- `bootstrap/db-tools.ts` + `workflow-tools.ts` 也都强制这些字段非空
- 因此"正常路径下"（用户使用 `gsd_plan_slice` 工具调用）validator 几乎总会 pass
- 仅当 LLM 绕过 tool 直接手改 `-PLAN.md`，或 tool schema 放行 `files: []` → validator 拒绝（见 P2-1）时才会遇到 `Result: fail`

**修复建议**（二选一）：

- **方案 A（推荐）**：`hasPhaseCompletionArtifact` 改为读 artifact 内容，解析首段的 `- Result: pass` / `- Result: fail`，只有 pass 才算完成。代码成本 ≤ 10 行。同时补测：在 `profile-dispatch.test.ts` 写一个 `Result: fail` 的 artifact，期望 advise。
- **方案 B**：validator 失败时**不写** `IMPL-PLAN-VALIDATION.md`，只写 `IMPL-PLAN-RETRY.md`。语义更直白（artifact 存在 = pass 语义），但与 v1.1 admission 的 "artifact 写入 + `Admission Decision: needs-rework`" pattern 略不同，需评估一致性。

**等级定为 P1**：正常路径下不触发；但 v1.3 明确是"把 P2/P3 从 soft 升到 strict"，gating 的严格度应当匹配宣称的语义，不应因为 artifact 的文字含糊而让 P3→P4 漏过。

### P1-2 ⚠️ 缺 "validator fail artifact 已写入后 profile-dispatch 行为" 的 negative 覆盖

**证据**：`profile-dispatch.test.ts:75-140` 只有两个双测点：

- 无 `IMPL-PLAN-VALIDATION.md` → advise `plan-slice`
- 存在 `IMPL-PLAN-VALIDATION.md`（内容任意）→ proceed

没有针对 `Result: fail` 的 artifact 场景的测试。配合 P1-1，此覆盖缺口是风险显性化点。

**修复建议**：若采纳 P1-1 方案 A，追加一条测试：artifact 存在但含 `Result: fail` → advise `plan-slice`。若采纳方案 B，则该测试退化为"artifact 不存在 → advise"。

### P1-3 ⚠️ 与 v1.1 admission 同形的 cycle 2 idempotency 限制仍在（框架级问题）

**证据**：v1.1 admission 评审 P1-3 已指出，`rule-registry.ts` 对 `artifact` 存在即跳过 hook 的 idempotency 策略，会让 `max_cycles: 2` 在实际运行中**不可能进入 cycle 2**（因为 cycle 1 已写入 artifact）。

v1.3 impl-plan-validator 复用同一框架：

- `preset.ts:56-63` 设置了 `max_cycles: 2`
- 但 rule-registry 的 idempotency gate 仍先于 built-in 短路生效
- 因此 cycle 2 在实际 runtime 几乎不会被触发，除非 validator 自己删除 `IMPL-PLAN-VALIDATION.md`

**差异**：相较 admission，impl-plan-validator 的失败 cycle 可以通过"手动/脚本删除 artifact + retry 触发"工作流，因为 `runPhaseDisciplineImplPlanValidatorHook` 每次执行都会 **overwrite** artifact（`writeFileSync` on same path）。但 overwrite 路径被 idempotency gate 挡住了，所以 cycle 2 不会自然发生。

**结论**：与 v1.1 相同，不是本次 v1.3 引入的新 bug，但本次 v1.3 扩大了受影响的 hook 数量。建议与 v1.1 P1-3 一起在框架层面修（要么 built-in 短路在 idempotency gate 之前，要么给 built-in hook 一个"由 handler 负责 cycle 生命周期"的逃生阀）。

### P2-1 ⚠️ `files: []` 的合法性在 tool / MCP schema 和 validator 之间不一致

**证据**：

- `plan-slice.ts:169-171`：`files.some((item) => !isNonEmptyString(item))`，空数组 `[]` 通过（`[].some(...) === false`）
- `workflow-tools.ts:871-872`：`nonEmptyStringArray = (field) => z.array(nonEmptyString(\`${field}[]\`))`，空数组通过（Zod `z.array` 默认允许空）
- `db-tools.ts:529`：`Type.Array(Type.String(), ...)`，同样允许空
- `impl-plan-validator.ts:43-45`：`!Array.isArray(...) || files.length === 0` → **拒绝空数组**

**影响**：

- 一个精心构造的 `gsd_plan_slice` 调用可以用 `files: []` 通过三层 schema，但会在 validator 端失败
- 失败后触发 retry + `IMPL-PLAN-RETRY.md`；retry cycle 依赖 LLM 自行修正 → 冗余一次 cycle
- 不是 bug，但"工具端允许空、validator 端拒绝空"的语义漂移会让行为难以预测

**修复建议**（二选一）：

- **方案 A（推荐）**：tool / MCP / DB schema 全部加 `min: 1` 约束，使得 `files: []` 直接被 tool 层拒绝。这样 validator 的 `files.length === 0` 检查就变成冗余防御（保留也无害）
  - `workflow-tools.ts`：`nonEmptyStringArray(field).min(1, { message: ... })`
  - `db-tools.ts`：`Type.Array(Type.String(), { minItems: 1 })`
  - `plan-slice.ts:169`：`files.length === 0` 显式抛错
- **方案 B**：放宽 validator，允许 `files: []`（承认 "pure doc/test slice 不改动源文件" 是合法场景）。但这与计划 §4.1 "`files: string[]`（预期修改文件列表）"的字面要求冲突，不推荐

### P2-2 ⚠️ 用户自定义 `builtin` hook 的 validate-time 保留问题（预存的技术债）

**证据**：见 §5 最后一段。`preferences-validation.ts` 的 `PostUnitHookConfig` 校验路径不显式拷贝 `builtin` 字段，仅靠 `preferences.ts:restoreMergedBuiltins` 恢复 preset 来源的 builtin。

- 用户若在 `.gsd/preferences.json` 手写 `builtin: "phase-discipline-impl-plan-validator"` 的 shadow hook（罕见但合法），validate 后 `builtin` 会被裁剪 → shadow 无法短路到真正的 built-in handler → 退化成 prompt-only，行为变形。

**影响范围**：理论场景，实际用户极少这么写；v1.3 本身仅通过 preset merge 路径注入，不受此影响。

**修复建议**：后续把 `PostUnitHookConfig` 的 validator 扩展到显式识别并保留 `builtin`（白名单校验）。属于独立技术债，不阻塞 v1.3。

### P2-4 ⚠️ prompt 字符串与 built-in 短路的可读性（小）

**证据**：
