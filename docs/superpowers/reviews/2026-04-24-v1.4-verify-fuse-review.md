## 4. 核心行为矩阵验证

以下组合均通过代码路径 trace 与测试断言验证：


| `verify_fuse_on_fail` | VALIDATION verdict             | 调度结果（dispatch guard）      | hook 产物                                | 综合结论                                  |
| --------------------- | ------------------------------ | ------------------------- | -------------------------------------- | ------------------------------------- |
| 未设置 / false           | `pass`                         | `complete-milestone` 放行   | `VERIFY-FUSE.md` Close Blocked: no     | ✅ 基线行为                                |
| 未设置 / false           | `needs-attention`              | 放行（进入 complete-milestone） | Close Blocked: no                      | ✅ 向后兼容                                |
| 未设置 / false           | `needs-remediation`            | 阻断（老 #2675 guard）         | Close Blocked: no（hook 不响应 preference） | ✅ 向后兼容                                |
| true                  | `pass`                         | 放行                        | Close Blocked: no                      | ✅                                     |
| true                  | `needs-attention`              | 阻断（verify-fuse guard）     | Close Blocked: yes + RETRY 文件          | ✅ 新 fuse 生效                           |
| true                  | `needs-remediation`            | 阻断（verify-fuse guard 先拦截） | Close Blocked: yes + RETRY 文件          | ⚠️ 优先级测试缺失，见 P1-4                     |
| true                  | VALIDATION 文件缺失 / verdict 无法解析 | 放行                        | hook 不会被触发（因无 validate-milestone 事件）   | ⚠️ "unknown 视为 pass"未在 spec 声明，见 P1-3 |


**dispatch guard 代码路径回溯**（`auto-dispatch.ts:938-967`）：

```ts
const hasExplicitValidationFailure = verdict === "needs-attention" || verdict === "needs-remediation";
const verifyFuseDecision = hasExplicitValidationFailure || verdict === "pass"
  ? shouldBlockMilestoneClose({ basePath, milestoneId: mid, validationPassed: verdict === "pass" })
  : { blocked: false };
if (verifyFuseDecision.blocked) {
  return { action: "stop", reason: ..., level: "warning" };
}
if (verdict === "needs-remediation") {
  return { action: "stop", reason: `...needs-remediation...`, level: "warning" };
}
```

**双路径阻断矩阵**：


| 路径                                                                                | 触发时机                                                | 依赖 preset                                          | 语义                                                             |
| --------------------------------------------------------------------------------- | --------------------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------- |
| A. dispatch guard（`auto-dispatch.ts` `completing-milestone → complete-milestone`） | 用户/auto-mode 请求进入 complete-milestone 之前             | ❌（preference 驱动，与 preset 解耦）                       | 硬阻断：返回 `{action:"stop", level:"warning"}`                      |
| B. post-unit hook（`phase-discipline-verify-fuse`）                                 | `validate-milestone` 完成后、`completing-milestone` 进入前 | ✅（需 `milestone_profile: "phase-discipline-8step"`） | 软产出：写 `VERIFY-FUSE.md`（决定记录）+ `VERIFY-FUSE-RETRY.md`（retry 意图） |


路径 A 是**实际生效的兜底**；路径 B 是**审计/文档产出**。二者现实联动（详见 P0-1）存在设计 gap。

## 5. 问题清单

### P0（必须在合并前修复）

#### P0-1 `max_cycles: 1` 导致 hook retry 永远不触发 → `VERIFY-FUSE-RETRY.md` 写入是死代码

**位置**

- `preset.ts:71` `max_cycles: 1`
- `rule-registry.ts:249-252`：
  ```ts
  const currentCycle = this.cycleCounts.get(cycleKey) ?? 1;
  const maxCycles = config.max_cycles ?? 1;
  if (currentCycle < maxCycles) { /* 触发 retry */ }
  ```

**事实**

- hook 首次运行后，`cycleCounts.get(cycleKey) === 1`（由 `_dequeueNextHook` 在 `line 201,205` 设置）
- `max_cycles = 1`
- 条件 `1 < 1` 恒假 → retry 分支**永远不会进入**
- 因此 `runPhaseDisciplineVerifyFuseHook` 里写 `VERIFY-FUSE-RETRY.md` 是**无任何后续消费的死操作**

**影响**

1. 代码读者会误以为 hook 能触发 `validate-milestone` 重跑，实际上不会
2. 文件系统残留 `VERIFY-FUSE-RETRY.md`，但 engine 不消费；下次手动触发 `validate-milestone` 时也不会因它而 retry（因为 retry 判定在 `_handleHookCompletion` 路径里，需要 hook 再次完成才检测）
3. 测试 `verify-fuse hook writes retry artifact when validate-milestone failed` 仅验证了文件写入，**没有验证 engine 实际会消费该文件触发重跑** —— 形成"测试过了但系统行为错误"的错觉

**根本问题**
v1.4 实际上采用了**"dispatch guard 硬阻断 + hook 仅做审计产物"**的架构。但 `retry_on` 字段的存在暗示了 hook 参与重试，两者语义矛盾。

**建议（二选一）**

**选项 A（推荐，最小改动）**：删除 hook 的 retry 机制，让 hook 只做审计

```ts
// preset.ts 中去掉 retry_on 和 max_cycles，或显式声明 retry 不生效
{
  name: PHASE_DISCIPLINE_PRESET_HOOK_NAMES.verifyFuse,
  after: ["validate-milestone"],
  prompt: "Record milestone verify-fuse decision ...",
  builtin: PHASE_DISCIPLINE_PRESET_HOOK_NAMES.verifyFuse,
  artifact: "VERIFY-FUSE.md",
  // 去掉 retry_on / max_cycles
}
```

同时在 `verify-fuse.ts` 中删除 retryPath 写入逻辑，或保留文件但在注释中明确"此文件当前不被 engine 消费，仅作为人类可读的提示"。

**选项 B**：把 `max_cycles` 提到 2，让 retry 实际生效一次

```ts
max_cycles: 2,
```

但这与 v1.1 admission 同构后会循环：`validate-milestone` → hook 检测失败 → 触发重跑 `validate-milestone` → 同样失败 → hook 再判断 cycle >= max 退出。对 LLM 用户来说是无意义重放（除非 prompt 明确要求修复验收问题）。

**选项 A 更符合当前架构意图**（dispatch guard 才是真正的阻断），建议采纳。

### P1（应在紧随补丁中修复）

#### P1-1 dispatch guard 的 `verdict === "pass"` 分支代码冗余、增加阅读成本

**位置**：`auto-dispatch.ts:944-950`

```ts
const verifyFuseDecision = hasExplicitValidationFailure || verdict === "pass"
  ? shouldBlockMilestoneClose({
      basePath,
      milestoneId: mid,
      validationPassed: verdict === "pass",
    })
  : { blocked: false };
```

**事实**：当 `verdict === "pass"` 时，`shouldBlockMilestoneClose` 内部因 `input.validationPassed === true` 立即返回 `{blocked:false}`（verify-fuse.ts:16-18）。这个分支是**无意义调用**。

**影响**：代码读者会花时间分析"pass 为什么也要进 fuse 判断"，实际什么也没做。

**建议**

```ts
const verifyFuseDecision = hasExplicitValidationFailure
  ? shouldBlockMilestoneClose({
      basePath,
      milestoneId: mid,
      validationPassed: false,  // 只有失败时才进判断，此处恒为 false
    })
  : { blocked: false };
```

顺带：既然入口条件已经确保了 validation 失败，`shouldBlockMilestoneClose` 的 `validationPassed` 入参其实可以去掉（或改成"告诉我为什么要 block"这类语义参数）。不过保留当前签名也可接受，因为 verify-fuse.ts 的 hook 路径也在复用同一函数。

#### P1-2 路径 A 与 路径 B 的职责分工未在代码注释/设计文档中声明

**事实**：

- dispatch guard（路径 A）是真正的阻断点，preference 驱动，与 preset 无关
- hook（路径 B）只写审计产物，不做实际拦截（详见 P0-1）

**影响**：后续开发者看到 `retry_on` + `max_cycles` 会以为 hook 参与阻断；看到 dispatch guard 里 import `phase-discipline/verify-fuse` 会以为路径 A 依赖 preset 被启用。实际二者都是误解。

**建议**：

1. `auto-dispatch.ts` 在 `shouldBlockMilestoneClose` 调用点加注释：
  ```ts
   // verify-fuse guard (v1.4): triggered by `verify_fuse_on_fail` preference;
   // independent of phase-discipline preset. When enabled, any non-pass
   // VALIDATION verdict blocks milestone close. See docs/.../specs/phase-discipline-preset.md §12.
  ```
2. `verify-fuse.ts` 顶部加模块注释，说明：
  - `shouldBlockMilestoneClose`：全局 fuse 判断，被 dispatch guard 使用（preset 无关）
  - `runPhaseDisciplineVerifyFuseHook`：preset 专属的 post-unit hook，仅产出审计 artifact
3. plan / spec 中对 v1.4 的"实际生效机制"做一次性澄清（见 P2-8）。

#### P1-3 verdict 为 `undefined` / `null` / `unknown` 时的 fuse 行为未在 spec 声明

**事实**：

- dispatch guard 只在 `verdict === "needs-attention" || verdict === "needs-remediation"` 时进入 fuse 判断；其他值（包括 `unknown`、`null`、`undefined`）全部放行
- hook 里同样只在 `hasExplicitFailureSignal` 时调用 `shouldBlockMilestoneClose`

**这是宽松解释**：VALIDATION 文件存在但没有 verdict frontmatter 的情况下，fuse 不生效。

**影响**：

- 规避了 LLM 产出 VALIDATION 文件时忘记写 verdict 导致的误阻断（好处）
- 但也打开了"删掉 verdict 绕过 fuse"的侧门（风险）
- 实际上现实情况中 `unknown` 的发生率应该很低，但**spec §12 没有声明这个语义**

**建议**

- 在 `specs/phase-discipline-preset.md §12` 的 v1.4 条目中补充一句：
  > Verify-fuse only activates on explicit failure verdicts (`needs-attention`, `needs-remediation`). Missing/unknown verdicts are treated as "no signal" and allow milestone close. This is by design: requires explicit `pass` is not enforced at v1.4 (reserved for v1.5 stricter mode).
- 考虑在 `verify-fuse.ts` 顶部 JSDoc 中同步说明

#### P1-4 测试覆盖缺失关键优先级与边界 case

**缺 case 1：verify_fuse_on_fail + needs-remediation 的优先级测试**

当前 dispatch guard 逻辑是"先判断 verify-fuse，后判断 needs-remediation fallback"。这意味着启用 fuse 后，`needs-remediation` verdict 的阻断 reason 会变成 verify-fuse 文案（而非老的 #2675 文案）。

`remediation-completion-guard.test.ts` 当前测了：

- `needs-remediation`（默认）→ 阻断（老 #2675 路径） ✅
- `verify_fuse_on_fail + needs-attention` → 阻断（verify-fuse 新路径） ✅
- `needs-attention` 默认 → 不被 fuse 阻断 ✅
- `pass` → 不阻断 ✅

**缺**：`verify_fuse_on_fail + needs-remediation` → 应该被 verify-fuse 分支先拦截，reason 包含 `verify_fuse_on_fail`，而非 #2675 文案。这个优先级断言缺失。

**建议**：添加 case：

```ts
test("verify_fuse_on_fail takes priority over needs-remediation fallback", async () => {
  // setup: preferences.verify_fuse_on_fail = true, VALIDATION verdict = needs-remediation
  // assert: action === "stop", reason 匹配 /verify_fuse_on_fail/
});
```

**缺 case 2：VALIDATION 文件缺失 / verdict=unknown 的 hook 行为**

`verify-fuse.test.ts` 未测：

- VALIDATION 文件不存在时 hook 产出的 artifact 内容（应为 `Validation Verdict: unknown`, Close Blocked: no）
- VALIDATION 文件存在但无 frontmatter 时的行为

**建议**：补一个 hook test 覆盖 verdict=null 情况。

**缺 case 3：dispatch guard 的 `shouldBlockMilestoneClose` 调用测试**

`remediation-completion-guard.test.ts` 是以 dispatch 入口测试的，但没有从集成角度验证"启用 fuse 后, M001 在 `needs-attention` verdict 下，调用 run-unit 完整走一遍，complete-milestone 不会被 dispatch"。现有测试偏向单元级断言，缺少端到端 trace。v1.1 admission 也有类似 gap（见其评审 P1-6），建议同一轮补齐。

#### P1-5 hook 未处理 "preference 被禁用但 artifact 已存在" 的清理

**事实**：如果用户先开启 `verify_fuse_on_fail: true` 跑了一次 validate-milestone（写入 `VERIFY-FUSE-RETRY.md`），然后关闭 preference 重新跑：

- hook 会再次执行（artifact `VERIFY-FUSE.md` 已存在 → 被 idempotency check 跳过，不再执行）
- 旧的 `VERIFY-FUSE-RETRY.md` 残留

实际上由于 P0-1，RETRY 文件本身就无效，这个问题的严重性被弱化。但从清理角度看，hook 应该始终反映"最新一次判断"。

**建议**：

- 选项 A：idempotency check 对 verify-fuse hook 放宽（每次 validate-milestone 完成都重跑 hook，覆盖 `VERIFY-FUSE.md`）
- 选项 B：在 `clearFile(retryPath)` 的同时也 `clearFile(artifactPath)`，让下一次 validate-milestone 触发重新写入
- 选项 C：合并到 P0-1 的选项 A 解决（删除 retry 机制后，问题主要剩 artifact 可能过期，可接受）

### P2（可在 v1.5 窗口一并处理）

#### P2-6 `auto-dispatch.ts` 反向依赖 `phase-discipline/verify-fuse.ts` 带来轻度架构污染

**事实**：plan §二 条 2 要求"不触碰 kernel（auto-dispatch.ts）"。当前实现违反此约束，kernel 侧 import 了 phase-discipline 子模块的函数。

**评估**：

- 单函数 import、无状态、纯数据读取，实际影响很小
- 但 `shouldBlockMilestoneClose` 本质上不特定于"phase-discipline 预设"——它是一个"milestone close preference guard"，属于通用能力
- 放在 `phase-discipline/verify-fuse.ts` 里意味着 dispatch guard 对 preset 子模块隐式耦合

**建议**：

- 把 `shouldBlockMilestoneClose` 迁移到 `src/resources/extensions/gsd/milestone-guards.ts`（新建）或直接放在 `auto-dispatch.ts` 内部
- `verify-fuse.ts`（phase-discipline 专属）只保留 `runPhaseDisciplineVerifyFuseHook`，并 import `milestone-guards.ts` 的共享判断逻辑
- 好处：dispatch guard 不再 import 预设子模块；preference 是全局语义这一事实变得可见

#### P2-7 dispatch guard 是 plan 范围外的新增路径

**事实**：plan §第五节 只要求"preference 字段 + verify-fuse.ts + preset hook"。dispatch guard（`auto-dispatch.ts:938-958`）是 codex 自主决定加的。

**评估**：

- 从正确性角度看，这是**必要的补救**：plan 方案 A 的原意是"通过 hook 的 retry 机制阻断流程"，但由于 max_cycles=1 的限制（见 P0-1），hook 实际无法阻断 → 如果没有 dispatch guard，启用 `verify_fuse_on_fail` 后 `needs-attention` verdict 仍会被 dispatch 到 complete-milestone。
- 所以 dispatch guard 是正确的补丁；但它**替代了** plan 的原方案，plan 和 spec 都没有同步更新。

**建议**：

- 把 plan §第五节 的"方案 A"改写为反映实际实现：
  > v1.4 实际采用"dispatch guard（硬阻断） + hook（审计产物）"双路径。hook 不触发 retry（max_cycles=1）。dispatch guard 在 completing-milestone → complete-milestone 规则中调用 `shouldBlockMilestoneClose`。
- spec §12 v1.4 描述中加一行："Implementation: verify_fuse_on_fail gates complete-milestone dispatch directly; additionally writes VERIFY-FUSE.md audit artifact after validate-milestone when the phase-discipline-8step preset is enabled."

## 7. 可运行完整性判断

**场景 1：用户未开启 preset、未设置 preference**

- dispatch guard 走 `verifyFuseOnFail=false` 分支 → 所有 verdict 都放行到老 #2675 路径 → 行为与 v1.0 baseline 一致 ✅
- hook 未被注入 ✅

**场景 2：用户启用 preset，但未开 preference**

- hook 每次 validate-milestone 结束都会跑，写入 `VERIFY-FUSE.md` Close Blocked: no
- dispatch guard 走 `blocked=false` 分支 → 与场景 1 相同 ✅
- 额外产出：`.gsd/milestones/M*/VERIFY-FUSE.md` 审计文件

**场景 3：用户启用 preset + 开启 preference**

- verdict=pass：放行 ✅
- verdict=needs-attention / needs-remediation：dispatch guard 阻断 + hook 写 Close Blocked: yes ✅
- 用户修复后重跑 validate-milestone：因为 `VERIFY-FUSE.md` 已存在（idempotency check），hook 不再触发 → **artifact 残留上次的 "Close Blocked: yes"**（见 P1-5）
- dispatch guard 每次都读 VALIDATION.md 最新 verdict，所以阻断/放行判断是正确的，只有 audit artifact 会过期

**场景 4：用户未启用 preset 但开启 preference**

- dispatch guard 仍生效（preference 驱动，与 preset 解耦）
- hook 未被注入 → 无 audit artifact
- ⚠️ 这个组合在 plan 里没讨论，但当前实现允许这样用；spec 需要声明这是否为 supported configuration

**结论**：场景 1、2、3（主线）正确；场景 3 有 artifact 过期问题（P1-5）；场景 4 可用但文档未声明。

## 9. 对后续工作的影响

**对 v1.5（plan 中未展开，预估为 strict verification 扩展）**：

- 若 v1.5 要做"verdict=unknown 也阻断"的 strict 模式，可以复用 `shouldBlockMilestoneClose`，只需新增 `verify_fuse_strict?: boolean` 或类似 preference
- dispatch guard 的入口条件需要扩展为 `hasExplicitValidationFailure || (strict && !isPass)`

**对 composed-lite 退役**：

- v1.4 的双路径设计（dispatch guard + hook）说明 preset hook 不能作为 process control 的唯一手段，必要时需要在 kernel dispatch 层兜底
- composed-lite 退役时如果涉及 milestone close 语义迁移，要复核是否需要类似的 dispatch guard 兜底

**对长期架构**：

- 建议在 v1.5/v2 考虑将"milestone lifecycle guards"集中到一个独立模块（如 `milestone-guards.ts`），而不是散落在 `auto-dispatch.ts` 的规则里。这会让 `verify_fuse_on_fail` / `needs-remediation` / `missing SUMMARY` / 等多个 guard 的组合关系更清晰。
