## 2. A/B/C/D 选型评审

### 2.1 最终排序


| 排名    | 方案                                                      | 评语                                                               |
| ----- | ------------------------------------------------------- | ---------------------------------------------------------------- |
| **1** | **C（`PreDispatchResult.fanOutSpec` + builtin 短路，当前选择）** | 当下唯一正确选项；kernel delta 窄到单 test suite 可覆盖；复用 v1 已建立的 builtin 短路模式 |
| 2     | A（通用 `action: "fan-out"`）                               | 只有 ≥ 2 个独立 preset 都需 fan-out 且行为差异大时才值得做；v1.5+ 议题                |
| 3     | D（滥用 `replace` + builtin）                               | 形状"像 C"但 carrier 语义错误；修到能跑只会逐步演化回 C                              |
| 4     | B（post-unit after `research-slice`）                     | 语义时序错误；只能做 "review"，做不了 "replace 主研究代理"；不应采纳                     |


### 2.2 拒绝 A 的理由成立

`PreDispatchHookConfig` 当前是纯声明式配置。fan-out 本质是 async executor，把它拉进通用 authoring grammar 会把 `preferences-validation`、`rule-registry`、`auto-dispatch`、`auto/phases`、handoff 推荐的全部 shared-harness 回归面一起扩面，完全不符合 "独立 track、最小 kernel 侵入" 的纪律。

### 2.3 拒绝 B 的理由成立

composed-lite 的 `p1-research.ts` 是 "fan-out **替代** 主研究代理的产出"，不是 "review 主研究代理的产出"。post-unit 在时序上做不到这件事，强行做等于引入 fake research-slice 主产出 + 再做合并，污染 research-slice 语义。

### 2.4 拒绝 D 的理由成立

`replace` 语义是 "换一个 unit 类型执行"，scout fan-out 既不是 unit，也不应伪装成 unit。把 `action: "replace"` + builtin 做短路会让 `dispatch-match` event、stuck detection、journal 全部报错 unit 类型。

### 2.5 C 案的合理性

- 与 `phase-discipline-profile-dispatch` 在 `rule-registry.evaluatePreDispatch()` 中的现有短路（332-344 行）完全同构，没有引入新的架构概念
- `PreDispatchResult` 已经在 v1.1 之前加过 `advise` / `advisedUnitType` / `advisedUnitId`（见 types.ts 现状），再加 `fanOutSpec?` 是同一模式的第二次扩展，不是第一次
- `fanOutSpec` 只在消费端（`runDispatch()`）被识别，kernel 不需要理解 fan-out 内部结构
- 计划 §1.2 列出的不改动清单（`auto-dispatch.ts` 规则、`PreDispatchHookConfig.action` union、`rule-registry.ts` 公开契约、`preferences` schema）完全守住

## 3. 必改项（实现前需要调整的 5 条）

### 3.1 `PreDispatchFanOutSpec.builtin` 字段应泛化为 `string`

计划 §3.1 写的是：

```ts
export interface PreDispatchFanOutSpec {
  builtin: "phase-discipline-scout-fanout";
  ...
}
```

**问题**：

- `types.ts` 是 `main` 侧 kernel contract，不应 import/拼写 `phase-discipline-`* 名称。从 v1 到 v1.4 一直在有意避免这件事。
- 后续若出现第二个 preset 想用同一机制（如未来某个 P3 fan-out），就必须改 kernel union 或另造字段。

**改法**：

- `builtin: string`
- consumer side（`runDispatch()`）做 `switch` 或 dispatch table
- 具名常量集中在 `phase-discipline/preset.ts` 的 `PHASE_DISCIPLINE_PRESET_HOOK_NAMES` 里
- 这样 kernel 只知道 "builtin marker + scout descriptors"，不知道 preset 名称

### 3.2 把 "builtin 返回 proceed 可继续组合" 这条语义变更的影响面讲死

计划 §3.2 提到要把 `rule-registry.evaluatePreDispatch()` 的 builtin 段从 "总是立即 return" 改成 "proceed 可组合"。这是一个**真实的 kernel 行为变更**，必须在实现前锁两件事：

1. **profile-dispatch 的 `proceed` vs `advise` 分支行为不能回归**：
  - 现在 `rule-registry.ts:332-344` 在 profile-dispatch 命中时无条件 return，包含 `action === "proceed"` 的场景。
  - 改成 proceed 时继续循环后，`firedHooks` 累加、`currentPrompt`/`currentModel` 合并的顺序都会变化。
  - 需要在 `rule-registry.test.ts` 显式锁定：profile-dispatch 返回 `advise` 时仍然立即 return（不会继续到 scout-fanout）；profile-dispatch 返回 `proceed` 时才继续组合。
2. **用户自定义 pre-dispatch hook 与 builtin 的相对顺序不能隐式改变**：
  - 现在 `modify` 的 append/prepend 语义靠累加 `currentPrompt` 实现（rule-registry.ts:357-365）。
  - 把 builtin 的 proceed 接入同一条累加路径后，要验证 `builtin proceed → user modify` 和 `user modify → builtin proceed` 两种 hook 顺序的语义不变。
  - `tests/merge.test.ts` 需要补齐这两种顺序的 case。

这不是否决改法，只是确保实现时这条被当作一级 invariant 来测，而不是 "顺手改一下 for loop"。

### 3.3 preset 中 scout-fanout hook 的 "carrier action" 必须显式写明

计划 §0.3 说：

> 该 hook 继续使用现有可通过校验的 action 作为 "carrier"，但真正行为由 `hook.builtin` 驱动。

但没有说用哪个。当前 `preset.ts:93` 里 profile-dispatch 用的是 `action: "advise"` 作为 carrier。scout-fanout 必须定死 carrier，并在计划里写清楚。两个可选：

- `action: "advise"`（与 profile-dispatch 对齐，但语义上 scout-fanout 不是 advise）
- `action: "modify"`（最通用、最无副作用；`prepend`/`append` 都可空）

**推荐用 `modify` 作为 carrier**。理由：

- 在 `rule-registry.ts:357-365` 里只会累加空字符串、不会走 `advise` 的 `advisedUnitType` 分支
- 即使未来有人误删 builtin marker，hook 也退化为一个无副作用的 modify，不会把 `research-slice` 错误 advise 成别的 unit

**必改**：计划 §2.1 和 §3.1 要显式写明 carrier action 的选择和理由。

### 3.4 fan-out 执行期间的并发安全与 cancellation 必须明确

`spawnGsdSubagent` 通过 `liveSubagentProcesses` Set 做全局 cleanup（subagent-spawn.ts:8-50）。并行 spawn 3 个 scout 时：

- `runPhaseDisciplineScoutFanOut()` 的 `Promise.allSettled` 返回后，即使某个 scout 已经失败，其他两个的 child process 仍会在 Set 中直到自然退出。
- fan-out failure 语义下，**剩余 scout 必须被主动 kill**，否则会出现 "失败后台仍在跑" 的幽灵场景。

计划 §3.3 的 executor 伪 API 没有提到超时与 cancellation。**必须补两条**：

- 任一 scout 抛错 → 立即 `kill` 其它 scout（通过 `trackLiveSubagentProcess` 返回的 unregister 或显式 `proc.kill("SIGTERM")`）
- 全部等待 `Promise.allSettled` 完成后再决定写不写 canonical artifact

放在 §3.3 或 §3.7 讲死即可。

### 3.5 `fanOutSpec` 与 non-proceed action 的互斥必须在契约上锁定

引入 `fanOutSpec` 后，类型上允许 `fanOutSpec` 和 `action: "advise" | "skip" | "replace"` 共存，但语义上必须互斥：

- `fanOutSpec` 只能与 `action === "proceed"` 共存
- evaluator 违反此约束视为 preset bug
- `runDispatch` 消费 fanOutSpec 的位置必须在 `return next` 之前、`prior-slice blocker` 之后，且**只在 action === "proceed" 时消费**（advise/replace/skip 都各自独立 short-circuit，fanOutSpec 应被忽略）

**必改**：

- types.ts 上加 JSDoc 注释标注此 invariant
- `runDispatch` 里添加 assert 或 defensive `if (preDispatchResult.action === "proceed" && preDispatchResult.fanOutSpec)` 守卫
- 计划 §3.1 contract 约束里显式写出：`fanOutSpec` 只能与 `action === "proceed"` 共存

## 4. 各重点问题逐项回应

### 4.1 "选 C 是否真是最小 kernel delta？"

**是，但需要 3.1 的泛化修正**。

kernel delta 列表：

1. `types.ts` 新增 `PreDispatchFanOutSpec` 类型 + `PreDispatchResult.fanOutSpec?`（additive）
2. `auto/loop-deps.ts` `runPreDispatchHooks` 返回类型扩展 `fanOutSpec?`（additive）
3. `rule-registry.ts` builtin composition 语义变更（behavior change，需 test 锁定）
4. `runDispatch()` 尾段新增 fanOutSpec 消费分支（additive）

其中 (1)(2)(4) 都是 additive，唯一真正的 behavior change 是 (3)。(3) 本身也是**有益的**——它让 builtin hook 与 user hook 的组合语义对称化（此前 builtin 永远短路，user 永远组合，是一个长期隐性不一致）。

### 4.2 "是否破坏现有 pre-dispatch / advise / runDispatch 不变量？"

**不破坏**，前提是：

- 3.2 的 test 锁定到位（profile-dispatch advise 仍立即 return）
- 3.5 的 action ≠ proceed 时忽略 fanOutSpec 守卫到位
- 3.3 的 carrier action 选择不与 advise 冲突

`honour-phase-discipline-advice` 规则、`advisedUnit.unitId` 回填、`dispatch-match` event、stuck detection、prior-slice blocker、`session.pendingVerificationRetry` 全部不动。

### 4.3 "fan-out 放在 `runDispatch()` 消费是否是最佳位置？"

**是**。候选位置对比：


| 位置                                                                  | 评价                                                   |
| ------------------------------------------------------------------- | ---------------------------------------------------- |
| `runUnit()` 内部                                                      | ❌ 那时 unit 已经开始编排，fan-out 应取代 unit 执行，位置太晚            |
| `dispatch-match` event 前                                            | ⚠️ 会跳过 stuck detection / prior-slice blocker，放弃了一层保护 |
| **stuck detection / prior-slice blocker 之后、`return next` 之前**（当前选择） | ✅ 保留所有 guard；fan-out 失败暂停也能走正常 pauseAuto 流程          |
| `runPreDispatchHooks` 结束后立即消费                                       | ⚠️ 同上，过早 short-circuit                               |


当前选择正确。唯一的小顾虑是 recentUnits 仍会记录被 fan-out 短路的 research-slice 一次——但这是**期望行为**（连续 fan-out 失败确实应该触发 stuck 诊断）。

### 4.4 "直接写 canonical `S##-RESEARCH.md` 是否合理？"

**合理**。理由：

- `auto-dispatch.ts:529` 的 `planning (no research) → research-slice` 规则完全依赖 `resolveSliceFile(..., "RESEARCH")` 是否存在来决定是否再次 dispatch research-slice
- fan-out 写这个文件后，下一轮状态推导自然掉到 `plan-slice`，无需动 `auto-dispatch.ts`
- 与 composed-lite 的 `writeArtifact(..., "research-brief", ...)` 做法本质一致，只是目标路径从 composed-lite 自用 artifact 换成 `.gsd` 主线的 canonical 位置

**注意点**（已在计划中，无需修，只是提醒）：

- fan-out 仅处理 `unitId === Mxxx/Syy` 形态，bypass `Mxxx/parallel-research`（auto-dispatch.ts:508）——否则并行 research 会变成 "并行 fan-out 套 fan-out"
- 失败时**不写** canonical 文件，保留 raw logs + 暂停 auto——这是严格失败语义，正确

### 4.5 "该方案是否会让 phase-discipline 后续版本演化更乱？"

**可控，但需要把 3.2 的 composition 语义变更固化到文档里**。

顾虑点：

1. `fanOutSpec` 命名具象到 "scout fan-out"，其他场景若需要并行产出（不一定是 scout）会复用得不那么自然——3.1 的泛化可缓解
2. `rule-registry.ts` 的 builtin composition 语义变更需要在 `phase-discipline/README.md` 和 spec §12 里留下一条清晰的 "pre-dispatch builtin composition contract" 描述，避免后续 v1.5+ 开发者误以为 builtin 永远短路
3. `runDispatch` 的 short-circuit 分支从 3 个（skip / advise / replace）变成 4 个（+ fanOutSpec），可读性略降——可通过抽一个局部 helper `applyPreDispatchOutcome()` 缓解，但不是必须

正面影响：

- 让 builtin hook 与 user hook 的组合语义对称化
- 建立了 "kernel-level generic field + preset-owned executor" 的可复用模式，未来 v1.5+ 再加 capability 时可参考
- 避免了 `action: "fan-out"` / `action: "replace"` 两种过度 kernel 化的脏方案

## 5. 可延后项

1. **Per-scout model fan-out**：计划明确 scope-cut 不做，合理。v1.3+ 若有需求再加 `cross_review_models`-style 字段
2. **structured JSON research brief**：现在只写 markdown，未来若 `plan-slice` 需要机器可读的 research 输入，再升级 schema
3. **raw log 轮转/压缩**：v1.2 一个 slice 生成 3 个 raw log 文件，可接受。R-12 size guard 思路适用
4. **fan-out observability JSON 与 `UnitMetrics` 的打通**：计划明确对齐 OQ-7 风格但不接 `auto-post-unit.ts`，正确——这是 v1.1 R-2 的延续
5. **skip-slice-research 与 scout-fanout 的交互**：当前 `prefs.phases.skip_slice_research: true` 会让 `planning → research-slice` 规则返回 null，research-slice 根本不会被 dispatch，scout-fanout evaluator 也不会跑。README 提一句即可
6. **把 `PHASE_DISCIPLINE_8STEP_SEQUENCE` 喂给 scout-fanout 评估 phase skip**：v1.2 不需要，profile-dispatch 已经处理 ordering

## 6. 不建议扩展的方向

几条可能冒出来但应立即 scope-cut 的想法：

- **不要** 把 `fanOutSpec` 写成通用 "任意 builtin callback" 接口（譬如 `runDispatch` 里用函数 pointer 查表）。现在 `if (preDispatchResult.fanOutSpec?.builtin === "phase-discipline-scout-fanout")` 就够；过早抽象会让 kernel 看起来 generic 但维护成本更高
- **不要** 把 scout-fanout 的 3 个 scout 任务暴露到 preferences schema。v1.2 是 deliberate scope cut，配置面扩大一次就收不回去
- **不要** 写 partial success（"2/3 scout 成功就合并"）。严格失败比侥幸 artifact 好管得多
- **不要** 顺便去改 composed-lite 的 p1-research.ts。这是独立 track，v1.2 只从它取形态参考，不动它的代码
